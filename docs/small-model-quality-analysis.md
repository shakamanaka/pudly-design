## Priorities for the same-model pipeline

1. **P0 — Close the real-model evidence gap before calling Haiku or Luna accepted.** Record the completed Haiku repair and review its saved desktop/tablet/mobile projections. Then run a small, repeatable prompt suite separately on Haiku and Luna, holding prompt, model, effort, app build, and viewport set fixed. Report first-draft and post-repair outcomes separately. Do not treat a passing fixture, valid JSON, a successful process exit, or structural QA as an aesthetic pass.
2. **P1 — Reduce the amount of design planning a model must keep in one response.** Explore a provider-neutral, typed page outline or section-by-section proposal that is internally assembled into one validated atomic batch before commit. Keep the selected provider/model pinned for repair, preserve cancellation/revision/scope checks, and retain the current no-partial-commit invariant. This is a proposal for an OpenSpec-backed change, not an implemented operation. First measure prompt/context bytes, output bytes, operation count, attempt duration, and repair count by model; do not infer tokens or billing from JSON character counts.
3. **P1 — Make the shared brief more executable for weaker models.** Use a short ordered checklist (page root → header → hero → primary content → trust/process → footer), and explicit per-section responsibilities, while retaining intent-based exceptions for component/minimal/edit requests. Avoid treating 25–45 nodes or 2–4 vectors as success targets: these are suggestions in the prompt, not quality measures. Compare the existing brief with the checklist in paired runs on the same short prompts before changing provider behavior.
4. **P2 — Add measurable responsive composition review.** Real browser review should check column width and text wrapping at 1440, 1024, 768, and 375 px; visual balance of repeated cards; hierarchy of headings/actions; and whether each authored illustration differs meaningfully from the others. Keep automatic checks limited to objective properties that can be measured consistently, and leave taste judgments to recorded independent human review.
5. **P2 — Separate image capability from illustration-count guidance.** The accepted run demonstrates editable vectors, not photographic or store-inventory imagery. Evaluate whether original vector scenes are distinctive enough for each prompt. If they are not, treat asset sourcing/upload as a separately specified product capability rather than encouraging more generic paths.

## Compact empirical rubric

Score each dimension 0–2 on the actual rendered page at desktop and mobile; inspect tablet separately for breakpoints. Record a short evidence note for every score. A run is a visual pass only when no dimension scores 0 and no critical overflow, clipped text, inaccessible action, or broken section order is present. Keep “first draft” and “after one repair” scores distinct.

| Dimension | 0 — fail | 1 — usable | 2 — strong |
| --- | --- | --- | --- |
| Readability | Clipped, overlapping, or hard-to-read text/actions | Readable with awkward wraps or dense areas | Clear type hierarchy, line lengths, contrast, and spacing |
| Responsive hierarchy | Mobile/tablet breaks or loses the main action/content | Fits but has cramped columns or uneven repeated items | Hierarchy and layout adapt cleanly at all reviewed widths |
| Domain relevance | Generic labels or misleading content | Recognizable domain with thin or generic details | Page-specific content, useful primary action, and appropriate supporting details |
| Imagery | Empty placeholders, emoji, or irrelevant shapes | Relevant but generic/simple authored imagery | Distinctive imagery that supports the brand and page story |
| Visual distinctiveness | Unstructured/default-looking or internally inconsistent | Coherent palette/layout with limited identity | Memorable art direction with consistent, purposeful variation |

Start with varied short prompts to expose dependence on a single pet-store brief: a neighborhood bakery storefront, a small independent bookstore, a yoga studio landing page, and a plant shop. Reuse the same assessment and desktop/tablet/mobile widths. Include one explicit text-only or minimal component prompt as a scope control, so stronger page guidance is not rewarded for expanding requests that should remain small.

## Recommendation

Do not claim smaller-model quality from the Sol acceptance. Finish and inspect the current Haiku repair, then establish a small real-run baseline for Haiku and Luna with the rubric above. If response burden remains a likely issue, prototype and specify a compact staged proposal that still validates and commits atomically; use per-run byte/operation/time measurements to decide whether it helps.
