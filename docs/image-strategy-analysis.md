# Image strategy analysis

Status: product and architecture recommendation, not an implementation specification. Reviewed 2026-10-13 against the current source tree, active `design-composition-quality` OpenSpec change, foundation contracts, and official provider/licensing documentation. No source behavior or capability is changed by this note.

## Current state: three different things are called “images”

The document schema has an `ImageNode` with a stable `assetId` reference and a `cover | contain | fill` fit ([architecture contract](architecture-contracts.md); `src/domain/types.ts`). That is a semantic placeholder for an asset, not an image payload or asset catalog. The current source tree has no `AssetStore`, upload route, asset metadata/bytes persistence, or resolver. The Vue renderer labels an image node “Image asset: …” rather than displaying pixels (`src/adapters/export/vue.ts`). Figma export likewise needs actual asset data to create an image; when data is missing it omits the layer and reports omission, per the export contract and tests.

By contrast, `VectorNode` stores bounded SVG path-command data plus a viewBox. Native vectors are real editable paths rendered in canvas/Vue and are currently the available authored visual-content route. They are not raster images, arbitrary SVG files, or a photo pipeline. Arbitrary SVG markup, URL attributes, and embedded image payloads are rejected. The active `design-composition-quality` change explicitly says “No photo asset pipeline” and recommends native illustrations for image-led briefs. Agent creation currently advertises frame, group, text, component instance, and vector; it does not advertise image creation. Therefore the accurate product statement today is: editable authored vector illustration is implemented, while user images, generated images, stock search, and photo rendering are not.

This distinction follows the core contract: DesignDocument owns stable semantics; renderers/exporters derive from it. Do not place binary image data in the document or present a reference-only ImageNode as if it could render.

## Claude Design comparison

Anthropic’s current Claude Design announcement says users can begin with a prompt, upload images and DOCX/PPTX/XLSX, or point Claude at a codebase; it also describes brand systems, web capture, live editing, and exports. It establishes that image upload is an input/reference workflow in that product. The public announcement does not specify whether uploaded images become reusable asset nodes, how stock sourcing works, or how generated image bytes are represented, so those internal details should not be inferred. [Anthropic: Introducing Claude Design](https://www.anthropic.com/news/claude-design-anthropic-labs)

For Codex Design, the useful product lesson is modest: accept visual references as prompt context, and separately make selected assets usable in the design. Upload-as-reference does not imply the image is already a renderable, exportable design asset.

## Image token and cost burden

A large file is not automatically a proportionally large vision-token bill. Current Anthropic vision documentation says images are processed in 28×28 patches; estimated visual tokens are `ceil(width/28) × ceil(height/28)`, subject to model-specific resizing and limits. For example, on the documented standard tier a 1920×1080 image is downscaled and costs about 1,560 visual tokens; high-resolution models may consume more. A 1000×1000 image is about 1,296 tokens. Two separate uploaded images roughly double image-token input, before prompt text and output. Exact API spend depends on the selected model’s current input price; Claude Code/subscription usage is governed by subscription limits and cannot be converted to a reliable dollar figure from this patch estimate alone. [Anthropic vision docs: resolution and token cost](https://platform.claude.com/docs/en/build-with-claude/vision)

These figures describe Claude API image inputs, not the current Codex Design runtime’s exact billing. Runtime providers may differ in image handling and accounting. Treat the estimates as a planning bound, not measured product telemetry. We have no Codex Design benchmark yet showing how many images a typical prompt includes, whether providers resend prior-turn images, or how much resizing changes visual quality. A future implementation should log sanitized per-request image count, dimensions after preprocessing, provider/model, and reported usage when available; do not log raw image contents. Measure representative prompts before choosing a hard quota. Keep source bytes available for display/export while sending a downsampled derivative for reference analysis where legibility permits.

## Recommended staged path

1. **Reference upload first.** Let the user attach a few local JPEG/PNG/WebP references to a generation request. Validate MIME by decoding content, pixel dimensions, byte size, and count; strip metadata where feasible; create bounded thumbnails; keep upload bytes outside DesignDocument. Send only the selected, resized references to the provider. Show users when an image is reference-only and when it will be inserted into the design. Define local retention/deletion and crash cleanup before accepting uploads. Do not silently make images part of later requests or cross-project context.
2. **Real asset store and image rendering.** Add an application-owned asset boundary with opaque stable IDs and metadata (media type, dimensions, checksum, byte length, origin, attribution/license/provenance, creation time). Store blobs outside the semantic document and reference by asset ID. Add a bounded asset resolver to canvas, Vue export, and Figma export. The current `ImageNode` shape can remain a reference, but validation must ensure every used asset resolves; exports must return explicit degraded/omitted fidelity on missing data. Image upload, asset registration, and node placement should be atomic from the user’s perspective and any document mutation must still go through validated revision-aware operations. Update contracts/specs before exposing image operations.
3. **Optional stock picker after asset/render pipeline.** Search stock explicitly on user intent, return source/photographer and terms in the picker, and require the user to choose an image before it is inserted. Keep stock search results as external references until selection; on selection, follow provider-required download/hotlink tracking and attribution behavior. Avoid unattended auto-selection in generation because relevance, licensing terms, and attribution are user-visible choices.
4. **Generated raster imagery later.** Add only after asset persistence, image resolution, export, cancellation, quotas, and provenance are working. Treat generated output as an asset with model/provider provenance, not as editable vector geometry. Generated and licensed stock content need separate origin metadata and policy handling.

## Stock sourcing and attribution implications

Pexels documents a search/photo API with API keys, image URL variants, a prominent “Photos provided by Pexels” link, photographer credit when possible, and default limits of 200 requests/hour and 20,000/month. Its license allows free personal/commercial use without required attribution, subject to restrictions (for example, no unmodified resale or misleading endorsement); API presentation rules still ask for Pexels attribution. This looks like a viable candidate for an explicit picker, subject to product/API approval and ongoing terms review. [Pexels API documentation](https://www.pexels.com/api/documentation/), [Pexels license](https://www.pexels.com/legal-pages/license/)

Unsplash has a broadly permissive content license, but its API rules add operational requirements: hotlink the returned image URLs, call its download endpoint for selection/use events, display photographer and Unsplash attribution with profile links and UTM parameters, protect API credentials (typically server-side), and avoid an automated or competing stock-library experience. Therefore “Unsplash license permits use” is not enough to establish an API integration is compliant. [Unsplash license](https://unsplash.com/license), [Unsplash API guidelines](https://help.unsplash.com/en/articles/2511245-unsplash-api-guidelines), [Unsplash API terms](https://unsplash.com/api-terms)

For either source, store provenance and source URLs with each selected asset and preserve a portable attribution record in project exports where practical. Do not promise that a user can sublicense stock content through a project export; preserve the original provider license and restrictions. Avoid caching or re-hosting API images unless the provider explicitly permits it. A legal review is appropriate before shipping a commercial stock connector because provider API terms change and may add obligations beyond the image license.

## Privacy and export boundaries

Uploaded references may contain confidential product screens, personal data, or unreleased brand material. Make the provider destination explicit, send only the requested images, and follow the selected model/provider’s data controls. Keep bytes, local paths, credentials, and raw provider envelopes out of DesignDocument and browser logs. Asset URLs from stock providers are untrusted external input; allow only approved schemes/hosts at the adapter boundary and do not embed arbitrary URLs in vector path data.

Native export should preserve image references and portable asset bytes through a documented bundle format or report a missing external dependency. Vue export should package or resolve a licensed asset according to its provenance rules. Figma export must receive actual bytes and report fidelity based on what it really imported; an `assetId` string alone is insufficient. Each export should include attribution/provenance metadata or an accompanying manifest when the selected source requires it.

## Measured current vector payload example

The accepted Sol6.1/low puppy-store run `e4a0ac86-80cb-43ca-b6fa-c9795fa2eff3` contains 38 lowered native operations serialized into 30,604 characters (compact JSON), with four pathData strings totaling 1,184 characters (299, 296, 265, 324). Path geometry accounts for approximately 3.9% of this particular lowered-operation character payload. This is not a token measurement, the original provider wire payload, reasoning compute or a vision-input bill. It suggests that in this simple illustration case, typed operation/layout verbosity is a larger payload contributor than path geometry. Detailed vector illustrations can behave very differently; measure actual provider usage before promising savings. Evidence: `.codex-design/quality-acceptance/1791924029466/evidence.json`.

## Product priority for the user's requested workflow

For improving actual output quality, implement upload-to-renderable-asset storage and image placement together as the first useful vertical slice; a reference-only attachment should not be presented as completion of user image support. Reference analysis is a separate optional use of an uploaded asset and should explicitly opt into sending it to the selected model. A small curated collection with recorded permissive licenses can be considered before an external stock API, but each asset still needs provenance, permitted redistribution/export and any attribution. This separates display/export bytes from model vision input and lets a smaller model select an existing image by opaque ID rather than authoring complex geometry.
