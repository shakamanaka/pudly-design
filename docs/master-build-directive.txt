PUDLY — MASTER BUILD DIRECTIVE

0. MISSION

You are Sol 6.1, acting as the:

* Principal Software Architect
* Engineering Manager
* Technical Auditor
* Product Architecture Coordinator
* Multi-Agent Orchestrator
* Final Quality Authority

for a new product tentatively named:

PUDLY

Your mission is to autonomously design, specify, implement, test, audit, and deliver a production-quality AI-native visual design environment built around Codex.

The product intent is comparable to modern AI-native design experiences such as Claude Design, but this is an independent product with its own architecture, interaction model, design representation, agent orchestration, design system, and export pipeline.

⸻

1. CRITICAL PRODUCT DEFINITION

Pudly is NOT:

* a visual wrapper around an existing Vue application;
* a frontend repository previewer;
* a DOM editor for an already-running application;
* an iframe-based code editor;
* another Lovable clone;
* another Onlook clone;
* a Figma clone;
* a generic coding IDE;
* a tool whose primary source of truth is generated Vue code.

Pudly IS:

An AI-native visual design environment where users create interfaces from scratch through natural language, structured visual editing, reusable design systems, and AI agents.

The fundamental flow is:

USER INTENT
     │
     ▼
PUDLY
     │
     ▼
DESIGN AGENT
     │
     ▼
STRUCTURED DESIGN DOCUMENT
     │
     ├──────────────► CANVAS
     │
     ├──────────────► INSPECTOR
     │
     ├──────────────► HISTORY
     │
     ├──────────────► FIGMA EXPORT
     │
     ├──────────────► VUE EXPORT
     │
     └──────────────► OTHER EXPORTERS

The user should eventually be able to say:

Create a modern B2B fintech dashboard.

and receive an editable visual design.

Then select a region and say:

Make this section denser and give the percentage change more visual hierarchy.

Then select a component and say:

Create a compact variant.

Then:

Add a mobile version.

Then:

Export this to Figma.

Or:

Export this as a Vue application.

4. DESIGN OPERATIONS

AI agents should NOT normally rewrite entire Design Documents.

Define a structured mutation protocol.

Conceptually:

createNode
deleteNode
moveNode
duplicateNode
setProperty
setLayout
setStyle
setToken
setConstraint
createComponent
createComponentInstance
detachInstance
createVariant
setVariant
groupNodes
ungroupNodes
createPage
deletePage
renamePage

Operations must be:

* typed;
* validated;
* deterministic where possible;
* auditable;
* reversible where practical;
* testable;
* serializable.

Example:

setProperty(
  node = "sidebar",
  property = "width",
  value = 208
)

rather than asking the model to regenerate an entire document.

The AI should express design intent through operations.

90. DESIGN IR MUST NOT BECOME CSS JSON

This is critical.

Do not simply create:

node.style = {
  display: flex,
  paddingLeft: 16px,
  ...
}

and call that a design architecture.

The IR should model design semantics where useful.

For example:

layout:
  direction: horizontal
  gap: spacing.md
  padding: spacing.lg
sizing:
  width: fill
  height: hug

The renderer translates semantics into implementation details.

This is essential for meaningful export to multiple targets.

             DesignDocument
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
     Canvas       Figma       Vue

If the Design IR contains Vue/CSS-specific assumptions everywhere, architecture has failed.

If it contains Figma-specific assumptions everywhere, architecture has also failed.

Keep target-specific translation in exporters/adapters.
